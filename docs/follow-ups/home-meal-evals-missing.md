# 추천·레시피·식단표 읽기 품질(AC14~AC19)을 eval로 증명하지 못함

**Symptom**: 스펙의 LLM 출력 품질 기준(겹침 0%, 식품군 95% 이상, 금지 메뉴 0%, 아이 안전 100%, 아침 10분 이하 90% 이상, 식단표 읽기 90% 이상)이 측정되지 않았다.

**Observed evidence**: 2026-11-19, 평가 사례(키즈노트 식단 25일치, 식단표 사진 5장)가 아직 준비되지 않아 사용자가 보류했다. 실제 무료 모델은 한 번에 하루치를 만드는 데 30~60초, 끼니 바꾸기에는 약 90초가 걸렸다. 프롬프트의 JSON 예시가 없으면 스키마와 다른 키로 답했다.

**Suspected cause**: 무료 모델은 게이트웨이가 JSON 스키마를 강제하지 않고(responseFormat 미지원) 응답이 느리다. 이 환경의 무료 OCR은 표로 된 한글 식단표에서 날짜별 칸을 자주 놓치고, 그 결과를 모델이 정리한다.

**What was tried**: 코드가 겹침·피할 음식·쉬는 메뉴·아이 안전·아침 시간을 검사해 어기면 다시 받고(최대 3번) 끝까지 어기면 내보내지 않는다. 식품군은 메뉴 이름과 재료로 코드가 다시 계산한다. 이 검사들은 단위 테스트로 증명했지만 모델이 처음부터 얼마나 지키는지는 측정하지 않았다.

**Proposed next step**: 평가 사례를 준비한 뒤 `llm-evals`로 AC14~AC19를 측정한다. 추천은 사례마다 3번씩 같은 조건으로 만들어 첫 시도 통과율과 재시도 뒤 통과율을 함께 본다.

**추가 관찰 (2026-11-19, 추론을 끈 뒤)**: `reasoning: "none"`으로 한 번에 5~6초가 되었지만 답의 절반쯤이 JSON으로 읽히지 않았다(`null`). 재시도 5번으로도 3일 중 2일은 150초 안에 추천을 만들지 못했다. 이때 화면은 "추천 실패"와 "다시 추천받기"를 보여 준다. `reasoning: "minimal"`은 20~36초, 기본은 40~50초(끼니 바꾸기는 최대 2.7분)였다.
